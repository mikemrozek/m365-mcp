## TL;DR

`fetchAllPages` no longer strands callers when it bails out on `maxPages` (100) or `maxItems` (10,000). The last-known `@odata.nextLink` is preserved on the response so the caller can resume, and a `_tsq_pagingBailedOut` marker is stamped on so the partial-result reason is unambiguous. Pre-existing bug; not introduced by tsq.5/tsq.6 — surfaced when delta tools hit large inboxes.

---

## The bug

`src/graph-tools.ts` previously had:

```ts
while (nextLink && pageCount < maxPages && allItems.length < maxItems) {
  // fetch next page, append to allItems, advance nextLink
}
// ...
delete combinedResponse['@odata.nextLink'];   // <-- unconditional
```

If the loop exited because the cap was hit (rather than because Graph stopped emitting `nextLink`), `nextLink` still held a valid resume token. The unconditional `delete` threw it away. The caller saw a `value` array with no `@odata.nextLink` and no `@odata.deltaLink` — stranded mid-sync, with no way to continue.

Most painful real-world trigger: `list-mail-folder-messages-delta` with `fetchAllPages: true` against a busy inbox — returned 10,000 items and no resume.

## The fix

In `executeGraphTool`'s pagination block (graph-tools.ts:399-490):

1. Hoist the cap check **into** the loop body, before fetching the next page. Set a `bailedOut: 'maxPages' | 'maxItems' | null` flag on bail.
2. After the loop: only `delete combinedResponse['@odata.nextLink']` when the loop exited naturally (Graph stopped emitting nextLink). If we bailed, **preserve** the most recent `nextLink` on the response.
3. Continue preserving `@odata.deltaLink` from any page that emitted one (unchanged behavior from tsq.6).
4. On bailout, stamp a diagnostic marker:
   ```json
   "_tsq_pagingBailedOut": {
     "reason": "maxPages" | "maxItems",
     "pageCount": <int>,
     "itemCount": <int>,
     "maxPages": 100,
     "maxItems": 10000,
     "note": "Returned partial results due to pagination cap. Use @odata.nextLink to resume."
   }
   ```
5. Single consolidated `logger.warn` on bailout (replaces the two prior post-loop warns).

**Diff size:** 1 file, +43/-8 lines. Scope is confined to the shared `fetchAllPages` block, so the fix applies to every tool that opts in to `fetchAllPages: true` — including all delta tools, `list-mail-messages`, `list-conversation-messages`, `list-drafts`, drive listings, etc.

## Behavior matrix

| Loop exit reason | `@odata.nextLink` in response | `@odata.deltaLink` | `_tsq_pagingBailedOut` |
|---|---|---|---|
| Graph stopped emitting nextLink (natural exit) | absent (deleted) | present iff any page emitted one | absent |
| pageCount reached maxPages | **present** (preserved for resume) | present iff any page emitted one | present (reason: `maxPages`) |
| allItems.length reached maxItems | **present** (preserved for resume) | present iff any page emitted one | present (reason: `maxItems`) |
| inner break (empty body / parse fail) | whatever the last assigned value was | unchanged | absent |

### Scenario B: large folder, cap hit — ⏳ NOT RUN

```
list-mail-folder-messages-delta
  mailFolderId: inbox          # assumes >10,000 items
  fetchAllPages: true
  select: id
```

**Expected:**
- HTTP 200
- Items returned up to the cap
- `@odata.nextLink` **present** (preserved for resume)
- `@odata.deltaLink` may or may not be present (only if any page emitted one before bailout)
- `_tsq_pagingBailedOut` marker present with `reason: 'maxItems'` (or `'maxPages'` if you hit page cap first)
- Log line: `fetchAllPages hit cap 'maxItems' (pages=N/100, items=10000/10000); preserving @odata.nextLink for caller resume.`
- Followed by: `Pagination complete: collected 10000 items across N pages (bailed out on maxItems)`

If inbox is under 10,000 items, you can temporarily edit `maxItems` lower (e.g. 50) just to trigger the bailout, then revert — the bailout reason in the marker will just say `maxItems` either way. Or use `list-mail-messages` against a busy folder.

Per the validation conversation on 2026-05-17, we chose to ship without running Scenario B: the natural-exit path validated by Scenario A exercises the same shared code; the bailout branch is a small, well-scoped conditional whose logic is straightforward to read in the diff; and if a real >10k-item delta call happens in production, the `_tsq_pagingBailedOut` marker and the `fetchAllPages hit cap` log line will surface it immediately.

### Resume continuity check (optional but recommended)
