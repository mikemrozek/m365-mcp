## TL;DR

`list-conversation-messages` now actually delivers `orderby`. The server strips `$orderby` from the outbound Graph call (which would otherwise 400) and sorts the response array client-side, marking the result with `_tsq_clientSorted`. tsq.6.1's `count: true` parameter is retained but no longer documented as the path to ordering.

---

## Root cause (why tsq.6.1's approach didn't work)

tsq.6.1 added `count: boolean` and a `ConsistencyLevel` header parameter to `list-conversation-messages` on the theory that Graph's advanced query mode (`ConsistencyLevel: eventual` + `$count=true`) would unlock `$filter=conversationId + $orderby`. Container log inspection (`/root/.ms-365-mcp-server/logs/mcp-server.log`) confirmed the server was correctly sending **both** advanced query parameters — and Graph **still** returned HTTP 400 `InefficientFilter`.

This is a **Microsoft Graph platform limitation**, not a server bug. Multiple Stack Overflow and Microsoft Q&A reports dating back to 2021 confirm: advanced query mode reliably unlocks `$filter` + `$orderby` for Entra ID directory objects (`/users`, `/groups`), but **not** for `/me/messages`. The combination is rejected even with all advanced query headers and parameters set.

---

## The fix

In `src/graph-tools.ts`, the `list-conversation-messages` handler now:

1. **Captures** `params.orderby` into a local `requestedOrderby` variable.
2. **Strips** `orderby` from `callParams` — it is never sent to Graph.
3. Calls `executeGraphTool(...)` as before (which now succeeds because no `$orderby` is in the query).
4. If `requestedOrderby` was set, parses the JSON response, sorts `parsed.value[]` by `field` and `direction` from the orderby expression, and re-serializes.
5. Stamps a `_tsq_clientSorted: { field, direction, note }` marker onto the response so downstream callers can detect server-side sort.
6. Wraps the sort in `try/catch` — any parse/sort failure falls back to the unsorted result and logs a warning.

The `count: true` parameter is **retained** (it still enables advanced query mode legitimately, which may be useful when combining with other features), but the tool description and `count.describe()` no longer claim it's the path to orderby.

## Behavior matrix

| Input | Outbound Graph URL contains $orderby? | Server sorts? | Marker in response? |
|---|---|---|---|
| no orderby | no | no | no — identical to tsq.6.1 |
| orderby (any) | **no** (stripped) | yes | yes: `_tsq_clientSorted` |
| orderby + fetchAllPages:true | **no** (stripped) | yes (after all pages merged) | yes |
| orderby + count:true | **no** (stripped) | yes; count also enables advanced query mode header | yes |

---

## Recommended caller pattern

For long threads, callers should pair `orderby` with `fetchAllPages: true` so the full set is sorted (not just page 1):

```
list-conversation-messages
  conversationId: <id>
  select: id,subject,from,receivedDateTime
  orderby: receivedDateTime desc
  fetchAllPages: true
```
