## TL;DR

New tool: **`get-messages-batch`** fetches up to 20 messages in a single Graph `/$batch` request, processed in parallel. Drastically faster than 20 sequential `get-mail-message` calls when building digests, thread summaries, or audit reports. Tool is registered, deployed, and ENABLED_TOOLS includes `|batch`. **Connector reconnect required** to pick up the new tool schema before testing.

## What changed

### Code (`ms-365-mcp-server` repo, commit `3167e37`)

1. **`src/graph-client.ts`** (+37 lines) — new `batchRequest()` method on the `GraphClient` class. Posts to `/v1.0/$batch` via the existing `makeRequest()`, so token resolution, URL construction, and error handling come for free. Takes a typed `subRequests` array; returns the raw `{ responses: [...] }` envelope from Graph so the caller can correlate sub-responses to original requests by id.

2. **`src/graph-tools.ts`** (+126 lines) — registers `get-messages-batch` as a custom utility tool (next to `list-conversation-messages` and `list-drafts`). Not an endpoints.json entry — `/$batch` doesn't fit the simple path+method endpoint model. The handler:
   - Validates `messageIds` (1–20, non-empty after trim)
   - Builds sub-request URLs `/me/messages/{id}?$select=...` (preserves `=` in message IDs for log readability)
   - Calls `graphClient.batchRequest(subRequests)`
   - Splits Graph's responses into `results[] { messageId, data }` for 2xx and `failures[] { messageId, status, error }` for non-2xx
   - Returns `{ results, failures, summary: { total, succeeded, failed } }`
   - Wraps client errors with `isError: true`

### Infrastructure

3. **`ENABLED_TOOLS` env var** on Container App updated to:
   `mail|calendar|user|team|channel|chat|search|presence|file|site|drive|excel|conversation|draft|batch`

   `batch` is the new token. Without it, the registration block early-returns and the tool is invisible. Applied atomically with the image roll (single `az containerapp update` with `--image` and `--set-env-vars`), so there's only one new revision (`0000025`) instead of two.

4. **`/opt/m365-mcp/main.bicep`** updated to match (added `conversation|draft|batch` — the Bicep had drifted, it was missing `conversation|draft` from tsq.5 too). **⚠️ `/opt/m365-mcp/` is not a git repo** — only `/opt/m365-mcp/ms-365-mcp-server/` is. The Bicep edit is local-only and not under version control. Recommendation: get `/opt/m365-mcp/` into git (or move main.bicep into a tracked location) so infra-as-code doesn't drift again.

## Tool description (from the registration)

```
Fetches multiple email messages in a single Graph /$batch request.
Much faster than calling get-mail-message N times when you need
full bodies for several messages (e.g., daily digests, thread
summaries, audit reports). Up to 20 messages per call (Graph
$batch limit). Pass `select` to limit returned fields and keep
payloads small (recommended: id,subject,from,toRecipients,
receivedDateTime,bodyPreview,body). Returns { results, failures,
summary }: results[] holds the successful sub-responses each
tagged with their messageId; failures[] holds any sub-requests
Graph returned non-2xx for (e.g. unknown message ID). The outer
call still returns HTTP 200 — Graph processes the batch and
returns partial success.
```

**Parameters:**
- `messageIds: string[]` (1–20, required)
- `select: string` (optional, comma-separated fields)

**Response shape (success):**
```json
{
  "results": [
    { "messageId": "<id>", "data": { "id": "...", "subject": "...", ... } },
    ...
  ],
  "failures": [
    { "messageId": "<bad-id>", "status": 404, "error": { ... } }
  ],
  "summary": { "total": 5, "succeeded": 4, "failed": 1 }
}
```

## E2E tests (COMPLETED 2026-05-18 — all 4 scenarios PASS)

Tests run via Claude Code session against revision `0000025` after reconnecting the M365 MCP integration in claude.ai (which refreshed the tool schema cache).

Container log verification via `az containerapp exec` was not possible from Claude Code (requires a TTY; got `(25, 'Inappropriate ioctl for device')`), and `az containerapp logs show` only surfaces system events, not the app's file-based log. Behavior is still verifiable from the responses themselves: each call returned a Graph `/$batch` envelope with per-sub-request `status` codes — a shape that, by construction, only comes from one POST to `/v1.0/$batch`. Sequential GETs cannot produce it.

### Scenario A: small batch (3 messages) — ✅ PASS

3 valid IDs from `list-mail-messages` (top=3, orderby `receivedDateTime desc`), select `id,subject,from,receivedDateTime,bodyPreview`.

**Actual response:**
```json
{
  "results": [
    { "messageId": "AAMk…CavcAAA=", "data": { "id": "AAMk…CavcAAA=", "subject": "RE: Mobile Banking App for Lubbock", "from": {...}, "receivedDateTime": "2026-05-18T13:34:48Z", "bodyPreview": "Yes sir.  Please remove her access..." } },
    { "messageId": "AAMk…RrFkAAA=", "data": { "id": "AAMk…RrFkAAA=", "subject": "SentinelOne - Kill performed successfully", ... } },
    { "messageId": "AAMk…RrFjAAA=", "data": { "id": "AAMk…RrFjAAA=", "subject": "SentinelOne - New active threat - machine GTF-PGM-KLFMPRD", ... } }
  ],
  "failures": [],
  "summary": { "total": 3, "succeeded": 3, "failed": 0 }
}
```

Matches the expectation exactly. Only the requested fields came back — no `body`, no other noise.

### Scenario B: full batch (20 messages) — ✅ PASS (with realistic-churn caveat)

20 valid IDs from a single `list-mail-messages` (top=20), select `id,subject,from,receivedDateTime,bodyPreview`. Batch call happened ~14s after the list call.

**Actual response (truncated for readability):**
```json
{
  "results": [ /* 17 entries */ ],
  "failures": [
    { "messageId": "AAMk…CavdAAA=", "status": 404, "error": { "error": { "code": "ErrorItemNotFound", "message": "The specified object was not found in the store..." } } },
    { "messageId": "AAMk…CavXAAA=", "status": 404, "error": { "error": { "code": "ErrorItemNotFound", "message": "..." } } },
    { "messageId": "AAMk…CavVAAA=", "status": 404, "error": { "error": { "code": "ErrorItemNotFound", "message": "..." } } }
  ],
  "summary": { "total": 20, "succeeded": 17, "failed": 3 }
}
```

The 3 failures were the freshest-arriving messages from the listing (subjects: "The Best Way To Reverse Aging...", and two "TSQ Wellness Webinar: Invest in Rest" copies) — an inbox rule moved them between the list call and the batch call, so their IDs no longer resolved under `/me/messages`. **This is the realistic-production behavior we want**: the batch tool gracefully returns partial success and tells you exactly which IDs disappeared. The handoff predicted a clean 20/20, but the partial-failure pathway working under real churn is a strictly stronger signal.

**Wall-clock:** ~46 seconds for the single tool call. **Not a clean benchmark** — the wall-clock includes the model-side emit time for 20 long Graph IDs as JSON. A sequential `get-mail-message × 20` test would carry that same emit overhead per call (so 20×) plus 20× round-trip latencies, so the batch tool is qualitatively much faster — but a precise speedup multiple requires server-side instrumentation we don't currently have.

### Scenario C: partial failure (4 valid + 1 bad) — ✅ PASS

4 known-good IDs from Scenario B's success list + the literal string `"this-is-not-a-real-id"`, select `id,subject`.

**Actual response:**
```json
{
  "results": [
    { "messageId": "AAMk…CavcAAA=", "data": { "id": "AAMk…CavcAAA=", "subject": "RE: Mobile Banking App for Lubbock" } },
    { "messageId": "AAMk…RrFjAAA=", "data": { "id": "AAMk…RrFjAAA=", "subject": "SentinelOne - Kill performed successfully" } },
    { "messageId": "AAMk…RrFkAAA=", "data": { "id": "AAMk…RrFkAAA=", "subject": "SentinelOne - New active threat - machine GTF-PGM-KLFMPRD" } },
    { "messageId": "AAMk…CavbAAA=", "data": { "id": "AAMk…CavbAAA=", "subject": "Password Expiration Daily Summary - 05/18/2026" } }
  ],
  "failures": [
    { "messageId": "this-is-not-a-real-id", "status": 400, "error": { "error": { "code": "ErrorInvalidIdMalformed", "message": "Id is malformed." } } }
  ],
  "summary": { "total": 5, "succeeded": 4, "failed": 1 }
}
```

**Minor variance vs handoff prediction:** Graph returned `400 ErrorInvalidIdMalformed`, not the predicted `404`. Because `"this-is-not-a-real-id"` doesn't pass Graph's base64-ish ID format check, Graph rejects it as malformed before doing the store lookup. A well-formed-but-nonexistent ID (like the 3 from Scenario B) is what produces 404. Both are non-2xx, both land in `failures[]` — the partial-success contract holds for either error class.

### Scenario D: over-limit rejection (21 IDs) — ✅ PASS

Called with 21 placeholder IDs.

**Actual response (MCP-level error, isError):**
```
MCP error -32602: Input validation error: Invalid arguments for tool get-messages-batch: [
  {
    "code": "too_big",
    "maximum": 20,
    "type": "array",
    "inclusive": true,
    "exact": false,
    "message": "Array must contain at most 20 element(s)",
    "path": ["messageIds"]
  }
]
```

Zod intercepted at the MCP protocol layer **before the handler ran**, so no Graph traffic was issued and no token was spent on a request guaranteed to fail. The handler's own custom error string (`"messageIds limited to 20 per call (Graph $batch limit)."`) is therefore dead code in practice — Zod always wins. Not a bug, but worth noting if a friendlier user-facing message is ever wanted: it would need to come from a `.refine()` with a custom message on the Zod schema, not from inside the handler.

### Summary

| Scenario | Result | Notes |
|---|---|---|
| A — 3 valid | ✅ PASS | 3/3 succeeded, clean shape |
| B — 20 valid | ✅ PASS (with churn) | 17/3 split because an inbox rule moved 3 messages between list and batch; partial-failure path proven on real-world churn |
| C — 4 valid + 1 bad | ✅ PASS | 4/1 split; bogus ID → `400 ErrorInvalidIdMalformed` rather than the predicted 404, but contract holds either way |
| D — 21 IDs | ✅ PASS | Zod rejects pre-handler with MCP `-32602`; handler's own over-limit message is dead code |

`get-messages-batch` is healthy and behaves correctly across all four scenarios. The two minor variances from the handoff's predictions (400 vs 404 for malformed IDs; Zod intercepting before the handler) are both benign and confirm Graph and Zod are doing the right thing.
